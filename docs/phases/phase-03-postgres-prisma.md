# Phase 03 — PostgreSQL + Prisma: client, tenant extension, migrations

## 1. Goal

Connect the API to PostgreSQL 17 through **Prisma 7.10.1**, set up **exactly as PaperTrail's
implemented code does**:
- `prisma.config.ts` and a schema with the generator, the datasource and the conventions comment,
  but **no models yet** (Phase 04 adds the first ones);
- `src/db/prisma.ts`, a COPY of PaperTrail's client **with the tenant extension**, `TENANT_MODELS` set
  to this project's tables;
- `db/errors.ts` (`isUniqueViolation`, `isRecordNotFound`, `isUuid`, `nullIfNotFound`);
- `utils/db/{transaction,cursor}.ts`: one way to run a transaction, one way to paginate;
- `config/db.ts`: connect at boot, disconnect at shutdown, `isDbHealthy()` for `/health`;
- `scripts/ensure-database.ts` and an empty baseline migration;
- a unit test of the tenant scope rules (`tenantOrgId`) that needs no tables.

## 2. What I will understand after this phase

1. Why PostgreSQL and not MongoDB here (PaperTrail ADR 0010: silent wrong queries, no foreign keys).
2. Why Prisma is pinned to 7.10.1 when npm's `latest` is 8.0.
3. How the tenant extension turns `findUnique({ where: { id } })` into "by id **and** in this
   business", and why a missing scope **throws** instead of returning everything.
4. Why raw SQL bypasses the extension, and the rule that follows.
5. Why races are settled by conditional updates and unique constraints, not by retrying transactions.
6. Why UUIDv7 ids make `(created_at, id)` cursors cheap.

## 5. Concepts

**Why PostgreSQL** (the spec asks for it, and PaperTrail learned it the hard way). Mongoose dropped
unknown filter keys, so `deleteMany({ documentId })` on a collection without that field deleted every
row in the org, and a dashboard counted a field that didn't exist and always showed 0. No foreign
keys meant hard deletes were ten hand-maintained `deleteMany` calls. This app's data is relational:
business → messages → AI results → reply, booking. With foreign keys and `ON DELETE CASCADE`, the
retention job (Phase 28) is one `DELETE FROM messages WHERE …`, and the database guarantees nothing
is left behind.

**Why 7.10.1.** npm's `latest` tag points at `8.0.0-rc.*`. The app is CommonJS, needs interactive
transactions and client extensions, and shouldn't depend on a pre-release API. PaperTrail made the
same call. Check `npm view prisma dist-tags` when you start; move to 8 only once it's stable, with
its own phase.

**The generated client lives in `src/generated/prisma`** (`provider = "prisma-client"`,
`moduleFormat = "cjs"`), is gitignored, and is regenerated by `postinstall` and `build`. Import it
from there, never from `@prisma/client`.

**The tenant extension** (`src/db/prisma.ts`, copied). Every query on a model in `TENANT_MODELS`
goes through `$allOperations`:
- reads, updates, deletes: `where` becomes `{ ...where, orgId }`. Since Prisma 5 a unique `where`
  accepts extra filters, so `findUnique({ where: { id } })` means "this id **in this org**". Another
  business's id is a 404, not a leak;
- creates: `data.orgId` is set. A different `orgId` in `data` throws `Cross-tenant write refused`;
- no org in the request context and no `runAsSystem()` → it **throws**
  `Tenant scope missing for Message.findMany`. Failing closed is the point: a forgotten scope is a
  crash in development, never a silent cross-business read in production.

The list is set now for **every** tenant table this project will have (data-model.md), even though
none exist yet. A model added later is scoped from the moment it exists:

```ts
export const TENANT_MODELS = new Set<string>([
    "Invite", "InfoEntry", "IntakeForm", "Message", "AiResult", "ModelCall", "OrgUsage",
    "Reply", "BookingRequest", "AuditLog", "OutboxEvent", "GmailConnection",
]);
```

Not tenant-scoped: `User`, `Session`, `VerificationLink`, `Org`, `Membership` (a user's memberships
span businesses), `EvalRun`, `EvalResult`.

**Raw SQL bypasses it.** `$queryRaw` doesn't go through `$allOperations`. Rule: **every raw statement
on a tenant table filters on `org_id` itself**, and the code review checklist (Phase 31) greps for
`$queryRaw` to check it. Stats (Phase 27) is the main user.

**`settleInScope`** (Phase 02's file). A Prisma query is a lazy thenable. Without it,
`runAsSystem(() => prisma.message.findMany())` would return the query unstarted, the scope would
end, and the query would then run with no context and throw. `settleInScope` starts it while the
scope is active.

**Transactions** (`withTransaction(fn)`, interactive, READ COMMITTED, 15 s timeout):
- use `tx` for every statement inside, or that statement runs outside the transaction;
- never call HTTP or enqueue a job inside. Write an outbox row (Phase 13) and let the relay do it;
- races are settled by the database: conditional `updateMany({ where: { id, status: "ready" } })`
  and unique constraints (`P2002` → `isUniqueViolation`). Approving a message twice (Phase 24) is
  one conditional update that matches 0 rows the second time.

**Cursor pagination.** Ids are UUIDv7, so they sort by creation time. `afterCursor` +
`cursorOrder` give stable pages on `(createdAt desc, id desc)`, matching composite indexes like
`(org_id, status, received_at desc, id desc)` on messages. No `OFFSET`, so page 50 costs the same
as page 1, and a new message arriving doesn't shift the next page.

## 9. Interview angle

*"How do you stop one business seeing another's messages?"* Not by remembering to add `orgId` to
every query. The Prisma client is wrapped in an extension that adds the caller's business to every
query on a tenant table. A `findUnique` by id becomes "by id and in this business", so someone
else's id is a 404. A create that names a different business is refused. A query with no business
in context throws instead of returning everything. Cross-business work like the retention job opts
out explicitly with `runAsSystem()`. Raw SQL bypasses the extension, so every raw query filters on
`org_id` by hand, and that's a review rule.

*"Why Postgres over Mongo?"* My PaperTrail project started on MongoDB and moved. Mongoose silently
dropped a filter key, and a delete wiped every webhook delivery in an org. Here messages, AI results,
replies and bookings form a tree. Foreign keys with cascade make retention one statement that can't
leave orphans, and unique constraints settle races (one reply per message, one email per Gmail id)
without application locks.
