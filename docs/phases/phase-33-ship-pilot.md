# Phase 33 — README, ADRs, demo, pilot kit

## 1. Goal

Turn a working system into something a reviewer, an interviewer and a business owner can each
understand in two minutes:

- **README** per spec §12, with the results table **generated** from `evals/FROZEN.json` (Phase 30);
- **ADRs** for the decisions an interviewer will ask about;
- `docs/{ARCHITECTURE,DATA-HANDLING,SECURITY,LIMITATIONS,INTERVIEW,PILOT}.md`;
- a seeded **demo business** with a read-only demo login, and a **1–2 minute demo video/GIF**;
- a **pilot kit** (spec §10): outreach message, a one-page offer, data-processing points for a written
  agreement, and a before/after measurement plan;
- the **resume bullet** (spec §13), filled **only** from the frozen data;
- tag `v1.0.0`.

## 5. Concepts

**The README** (spec §12, in this order):
1. One line: what it does, and "a human approves every reply".
2. A demo GIF: widget submit → the draft appears with a highlighted flag → edit → approve → sent.
3. **Results (test set)**, generated by `pnpm --filter api eval:readme`. Every cell carries its `n`,
   and the caption names the run ids, split, date, models and prompt versions:

   | Step | Metric | Result |
   | --- | --- | --- |
   | Classify | Category accuracy | `category_accuracy` |
   | Extract | Field accuracy / valid JSON | `field_accuracy_mean` / `valid_json` |
   | Draft | Approved without edits | `approved_without_edits` |
   | Draft | Invented numbers caught by checks | `checks_recall` (planted) · `invented_rate` (reviewed) |
   | Draft | Injection attempts followed | `injection_followed` (injection set) |
   | Overall | Cost per 100 messages / p95 time to draft | `cost_usd_per_100` / `p95_ms_to_draft` |

   Plus one line on label agreement (κ from Phase 29) and a link to the published Prompt Lab runs.
4. How the pipeline works (the diagram from `docs/ARCHITECTURE.md`).
5. Prompt design decisions: separate steps, info-sheet-only facts, no booking promises, customer text
   as data.
6. Top mistakes found and how prompts were improved (from `EXPERIMENT.md`, with deltas).
7. Privacy and safety (summary + link to `DATA-HANDLING.md`).
8. How to run it (`docker compose up -d`, migrate, seed, `pnpm dev`).
9. Pilot results, **only** with the owner's written permission. Otherwise the section says "No pilot
   yet".

Then "Built on": e-commerce (origin), PaperTrail (the Postgres foundation), CounselDesk (widget),
Prompt Lab (evaluation), with links to the live demo and the Playbook lessons that use this project's
evals.

**ADRs** (half a page each, PaperTrail's ADR format: Status · Context · Decision · Alternatives ·
Consequences · How we'd know we were wrong):

| ADR | Decision | The alternative it beats, and why |
| --- | --- | --- |
| 0001 | PostgreSQL 17 + Prisma 7.10.1 | MongoDB (the archived plan): relational data (business → messages → AI results → replies → bookings), foreign-key cascades make retention one delete, and PaperTrail found schema-less queries "succeeding" wrongly (its ADR 0010). Prisma 8 RC: pre-release |
| 0002 | One checkpointed `process-message` job | A BullMQ flow of four jobs: steps are sequential and small; checkpoints give resume-after-crash without the moving parts |
| 0003 | The only send path is the approval transaction's outbox event | Sending from the controller: a crash between commit and send loses or duplicates replies; with the outbox and `jobId`, exactly-once and testable (Phase 31's import-graph test) |
| 0004 | A business is a PaperTrail org; `Org`/`orgId` names kept | Renaming to `Business`/`businessId`: every tenancy file stops being COPY, and the cross-tenant tests stop porting unchanged; the UI says "business" |
| 0005 | Info-sheet selection by type + keyword, no RAG | Embeddings + vector search: the sheet is tens of entries; selection is explainable and testable; "retrieval when a sheet passes ~N entries" is the stated trigger |
| 0006 | NVIDIA NIM with per-purpose models + fallbacks | One big model for everything: classify/extract measured on the cheap tier within the pre-written threshold (Phase 30), at lower cost per 100 |
| 0007 | Widget retries deduped by `clientSubmissionId` + a unique index | PaperTrail's idempotency-key middleware: one public endpoint, no response replay needed; the database settles races |

**LIMITATIONS.md**:
- one demo business; labels written by one person (with the κ figure);
- the restricted-scope Gmail verification needed before a public launch;
- polling latency up to ~60 s;
- no calendar sync, no WhatsApp;
- the checks can over-flag plain numbers (measured false-alarm rate);
- NVIDIA prices are reference prices with a date;
- Hinglish coverage only as wide as the test set;
- the judge, if adopted, is a second opinion in reports only.

**The demo.**
- `seed-demo.ts` reuses Phase 12's `seed-demo-business` (CodeNest, `isDemo = true`, so Phase 25's
  recording transport is used and nothing reaches a real inbox), then Phase 23's `seed-messages.ts` for
  15 sample messages, which reach the inbox through the real pipeline (replay provider).
- A **viewer** demo login (`demo@…`, published in the README) sees the inbox, flags, bookings and stats
  but can't approve, send or change settings. That's the role system, not a special case.
- The demo widget lives on a page on the web app's domain, so visitors can submit and watch it arrive.
  Demo messages are purged nightly.
- `demo-script.md` (ADAPT PaperTrail's) holds the 90-second walkthrough the GIF follows.

**Pilot, honestly** (spec §10), in `PILOT.md`:
- **Outreach** (in person first, then this message, 3 sentences): "I've built a tool that drafts
  replies to your website and email enquiries using only the facts you give it. You approve every
  reply before it goes out. Can I set it up free for two weeks and show you the reply times
  before and after?"
- **The one-page offer**: the promise is "faster, consistent replies; you approve everything", not
  "replaces staff". Setup covers the info sheet with the owner, tone guide, widget install, Gmail
  connect, retention and staff accounts. Two-week free pilot. Pricing is discussed only after the
  pilot shows value.
- **Points to agree in writing** (not legal advice; the owner may want their own adviser):
  - who processes messages (your deployment; NVIDIA as the model provider) and where;
  - the retention period;
  - who pays model usage (the business's monthly budget cap);
  - deletion on request and at the end of the pilot;
  - no use of their customers' messages in your test set or screenshots without separate written
    permission, with personal details removed;
  - either side can stop at any time.
- **Measurement plan**:
  - **two weeks before**: from the business's own inbox and form records, the median and p90 time
    to first reply, and unanswered messages;
  - **two weeks after**: the same, from `Reply.approvedAt − Message.receivedAt` and Phase 27's stats;
  - also: drafts approved without edits, top edit reasons.
  - Report medians with n. Small samples are labelled as such.

**The resume bullet** (spec §13). Fill it from `FROZEN.json` and the README only. A clause is
dropped, not guessed, if it has no data:

> Built an AI enquiry assistant (Next.js, TypeScript, Express, PostgreSQL/Prisma, BullMQ) that
> classifies small-business customer messages, extracts booking details and drafts replies from the
> business's own info sheet with human approval; on [N] labelled test messages it reached [X]% category
> accuracy, [Y]% of drafts approved without edits and [Z] invented prices reaching approval after
> code-level fact checks[; piloted with a local business, cutting median reply time from [A] to [B]].

**INTERVIEW.md**: spec §14's questions answered from your own numbers (≤ 5 sentences each), plus the
backend questions this build makes you ready for:

| Question | What the answer covers |
| --- | --- |
| Why split into classify, extract and draft? | testable steps, a cheap model where it's enough (Phase 30 table), clearer failures |
| How do you stop invented prices or times? | info-sheet-only prompt, code checks on every number (recall on planted cases), server re-checks edits, human approval |
| Why a human in the loop? | trust, cost of mistakes, edits become prompt improvements |
| How did you measure quality? | labelled set, κ, blind review, frozen test run |
| Prompt injection? | delimiters, data-not-instructions, checks for its effects, the 24-message set result |
| Informal or mixed-language messages? | tagged examples, per-tag accuracy |
| Cost control? | per-purpose models, cost per 100, monthly budget per business |
| How is "never auto-send" enforced? | outbox-only send path + import-graph test + behavioural test |
| What happens if the API crashes after approval? | the outbox row is in the same transaction; the relay sends; `jobId` prevents a double |
| How does tenancy work? | Prisma tenant extension scoped by request context; cross-tenant 404 suite |
| How are Gmail tokens protected? | sealed with AES-256-GCM, key outside the DB, narrowest scopes, revoke on disconnect |
| What would you add next? | calendar sync, WhatsApp, retrieval for large sheets, learning from edits |

## 9. Interview angle

Lead with the rule: *"The AI never sends anything on its own and never invents facts."* Then show the
mechanism. The only send path is an approval transaction's outbox event, and a test fails if anyone
adds another. Code checks every number against the info sheet, including numbers a person typed.
Customer text is wrapped as data. Then the evidence: the frozen test results, label agreement, the
injection set. Finish with the honest part: the limitations file, and, if you have one, a pilot's
before/after reply time reported as a median with its sample size.
